# 启动配置问题修正

日期：2026-10-29。问题来自同一 Docker 中两个目录共用 `material-studio` 项目名：新副本使用示例密码，旧 MySQL 卷仍保存初始化时的密码，健康检查重复等待后报 unhealthy。

## 修正

- 推荐启动入口改为 `bash scripts/up.sh`，`make up` / `make db` 使用同一检查逻辑。
- 先验证配置、拒绝空/占位密码，再检查现有容器的 Compose 工作目录，防止另一个副本直接替换正在运行的同名项目。
- 对运行中的 MySQL，使用目标配置实际登录应用用户和 root，验证通过后才更新容器。错误密码不触发重建；首次初始化/已停止的数据库则先启动 MySQL 再验证连接。
- 密码从 Compose 渲染结果读取，通过 stdin 传给容器客户端，不 source/eval `.env`，不写进命令参数或日志。
- MySQL 健康检查保留错误输出，便于查看 Access denied 等具体原因。
- 项目名可通过 COMPOSE_PROJECT_NAME 配置，原默认值保留，避免升级时切换既有卷。README 补充不同项目名/端口、旧卷密码与故障排查步骤。
- 新增独立 CI 作业检查脚本、9 项启动回归和 Compose 配置。

## 验证

9 项回归全部通过，覆盖示例密码、缺少配置、另一目录冲突、应用/root 错误密码、库名不符、首次初始化等待、Compose 参数、仅启动数据库和 Docker 不可用。断言错误诊断不泄漏密码，且不会删除数据卷。

另使用唯一命名的临时 Compose 项目实测三服务启动、错密码拦截、恢复配置和原数据读取。已有用户实例未被重启或修改。测试结束仅清理本轮创建的临时资源。

实测：[JSON 记录](evidence/startup-regression.json)。缓存已存在时完整启动约 30 秒，运行中数据库的错误密码约 0.54 秒内被识别；这些是本机测量，不是其他机器的耗时承诺。表中测试行在失败前后保持存在，恢复配置后三模板接口正常。

此修正保留标准 `docker compose up --build -d --wait`；推荐脚本提供额外的前置诊断。不会自动修改数据库密码、恢复丢失凭据或删除历史卷。真实 `.env` 仍不提交。
